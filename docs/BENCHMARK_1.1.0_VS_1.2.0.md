# dcd-lago 1.1.0 versus 1.2.0

A fixed comparison between two releases. **1.1.0** is the wheel installed from PyPI into its own virtualenv. **1.2.0** is this tree at commit `0384e9a`, measured twice: as **pure Python** (`LAGO_CORE=python` -- what a source install without a C compiler gets) and **compiled** (the compiled modules and the Cython metric kernel -- what the binary wheels give). The three run in separate processes on the same inputs: every stream is generated once as a list of links and handed to each side in the same order; `lago_modules` is timed on a freshly built stream, then `longitudinal_modularity` on the result (first call, and steady state). Every returned partition is scored with the 1.2.0 metric so that quality is compared with one yardstick.

For what to expect today, read [`PERFORMANCE.md`](PERFORMANCE.md) first; this report is the evidence behind its numbers.

Generated by `benchmarks/bench_pypi.py`; raw results in `benchmarks/results`.

Two things to keep in mind when reading the partitions column:

* 1.1.0 is **not deterministic** (its hashing follows memory addresses, bug B3 of round 1), so its partition can differ from run to run; 1.2.0 is deterministic;
* round 1 fixed nine latent bugs in the search, some of which change the result on specific inputs (k-partite null model, delayed duplicates, pop-order durations, ...). "same partition" is therefore informative but not required; the L-modularity columns are the quality comparison.

## Headline

* **Speed, `lago_modules`.** Over the 357 matrix-tier runs 1.1.0 finished (every parameter combination, 15 streams of 500–2 100 interactions), 1.2.0 is **7.8× faster in pure Python and 12.4× with the compiled core** (geometric means); the range across parameter combinations is 4–11× per stream in pure Python. On the scale tier (4k–96k interactions, default parameters) the speedup is 6–72× pure and 9–109× compiled, and it grows with size on wide streams: 1.1.0 is superlinear there, 1.2.0 is not.
* **1.1.0 timeouts.** 4 runs did not finish within 900 s: `continuous-S MM/STEM/full/in`, `continuous-M MM/STEM/full/in`, `continuous-M MM/STNM/fast/out`, `wide-100k MM/STEM/fast/in`. The two on continuous streams of a few hundred interactions are the oscillation behaviour fixed in round 1 (moves undone and redone; bug B6, id()-keyed caches), not size.
* **Quality, by the 1.2.0 metric.** Of 380 runs where both finished, 1.2.0's partition scores higher than 1.1.0's in 142, the same (±1e-4) in 161, lower in 77. 1.1.0 is not deterministic, so its numbers are one draw; the differences either way are those of a greedy search taking another path, plus the round-1 bug fixes on the inputs they concern.
* **Same partition as 1.1.0** in 155/380 runs (see the caveats above on why this is informative, not required); **1.2.0 pure and compiled identical in every run** (last section).
* **Metric.** `longitudinal_modularity` is 1.5–2.5× faster in pure Python and 10–70× faster in steady state with the compiled core and kernel (section 3).
